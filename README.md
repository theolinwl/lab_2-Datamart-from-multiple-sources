# Лабораторная работа №2
## curl, SQL JOIN и объединение данных из нескольких источников

Проект демонстрирует загрузку данных из нескольких источников (CSV, REST API и SQLite), проверку качества ключей, объединение таблиц средствами Pandas и SQL, построение витрины данных и визуализацию результатов.

## 1. Структура проекта

```text
lab2/
├── data/
│   ├── raw/
│   │   ├── organizations.csv
│   │   ├── regions.db
│   │   └── cleaned.db          # создаётся при запуске
│   └── processed/
│       ├── data_mart.csv       # создаётся при запуске
│       └── data_mart.parquet   # создаётся при запуске
├── results/
│   ├── plots/
│   │   ├── region_totals.png
│   │   └── top_organizations.png
│   ├── curl_commands.txt
│   ├── protocol_comparison.md
│   └── dashboard.png  # дашборд из PowerBI
├── src/
│   ├── loaders.py
│   ├── transform.py
│   └── database.py
├── main.py                     # FastAPI-приложение
├── lab_2.py                    # основной сценарий выполнения
├── requirements.txt
└── README.md
```

Файлы `organizations.csv` и `regions.db` должны находиться в `data/raw/`. REST API запускается из `main.py`. Файл `cleaned.db`, витрина и графики создаются программой автоматически.

## 2. Требования

- Python 3.10 или новее.
- Установленные зависимости из `requirements.txt`.
- Для выполнения `lab_2.py` должен быть запущен FastAPI-сервер.

## 3. Установка и запуск

Команды ниже приведены для Windows и выполняются из корневой папки проекта - той, где находятся `main.py` и `lab_2.py`.

### 3.1. Создание виртуального окружения

```bash
python -m venv .venv
```

Активация в Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Активация в Windows CMD:

```cmd
.venv\Scripts\activate.bat
```

Если используется Git Bash:

```bash
source .venv/Scripts/activate
```

### 3.2. Установка библиотек

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 3.3. Запуск REST API

Открываем первый терминал в корневой папке проекта, активируем виртуальное окружение и выполняем:

```bash
uvicorn main:app --reload
```

После запуска API будет доступно по адресу:

```text
http://localhost:8000
```

Проверить получение транзакций можно по адресу:

```text
http://localhost:8000/api/transactions
```

Документация Swagger:

```text
http://localhost:8000/docs
```

Оставляем этот терминал работающим, пока выполняется основной скрипт.

### 3.4. Запуск обработки данных

Открываем второй терминал в корневой папке проекта, активируем то же виртуальное окружение и выполняем:

```bash
python lab_2.py
```

Скрипт последовательно выполнит этапы C–H. Результаты и диагностическая информация будут выведены в терминал, а файлы витрины и графиков сохранены в соответствующих папках.


## 4. Этапы работы и результаты

### Этап C. Загрузка источников в Python

Данные загружаются из трёх источников:

- `organizations.csv` - сведения об организациях;
- REST API `GET /api/transactions` - сведения о транзакциях;
- `regions.db`, таблица `cities` - сведения о городах и регионах.

Для каждой таблицы выводятся размер, типы данных, первые строки, количество пропусков, полных дубликатов и уникальных значений ключевого столбца.

### Этап D. Проверка и очистка ключей

Ключевые столбцы приводятся к числовому типу `Int64`, при этом некорректные значения преобразуются в пропуски. Затем проверяются пропущенные и повторяющиеся ключи, сравниваются множества ключей и определяется кардинальность связей.

Полученные результаты:

- В `organizations` - 50 строк, 50 уникальных `org_id`, полных дубликатов нет.
- В `transactions` до удаления дубликата - 254 строки и 253 уникальных `transaction_id`; обнаружена одна полностью повторяющаяся строка.
- В `cities` - 20 строк и 20 уникальных `city_id`.
- У организации `org_id = 50` нет транзакций.
- В транзакциях присутствуют `org_id = 998` и `org_id = 999`, отсутствующие в справочнике организаций.
- В справочнике городов есть `city_id = 116` и `city_id = 120`, на которые не ссылаются организации.
- Связь организаций и транзакций - `1:N`.
- Связь организаций и городов - `N:1`.

Повторяющаяся полная строка транзакции удаляется перед объединением методом `drop_duplicates()`. После удаления остаётся 253 строки. Повторения `org_id` в таблице транзакций и `city_id` в таблице организаций сами по себе не являются ошибками: они соответствуют связям `1:N` и `N:1`.

### Этап E. Объединение средствами Pandas

Выполняются следующие операции:

1. `INNER JOIN` организаций и транзакций.
2. `LEFT JOIN` организаций и транзакций.
3. `LEFT JOIN` полученного набора со справочником городов.

Для объединений используются `indicator=True` и `validate`, чтобы контролировать типы связей и диагностировать несовпадающие ключи.

Результаты:

- `INNER JOIN` организаций и транзакций - 251 строка.
- `LEFT JOIN` организаций и транзакций - 252 строки.
- Последовательный `LEFT JOIN` с городами - 252 строки.

Две транзакции с неизвестными организациями не попадают в объединение, начинающееся с таблицы организаций. Организация без транзакций сохраняется в результате `LEFT JOIN`.

### Этап F. SQL JOIN и агрегация

Таблицы организаций, транзакций и городов загружаются в `data/raw/cleaned.db`. Далее выполняются SQL-запросы с `INNER JOIN`, `LEFT JOIN`, `GROUP BY`, `COUNT`, `SUM` и `AVG`.

Результаты SQL-соединений совпадают по количеству строк с соответствующими результатами Pandas:

- `INNER JOIN` - 251 строка;
- `LEFT JOIN` - 252 строки;
- последовательные `LEFT JOIN` - 252 строки.

Агрегаты по `org_id` рассчитываются двумя способами: SQL и Pandas. Сравнение целочисленных значений выполняется точно, а для сумм и средних используется `numpy.allclose()` с допуском из-за возможных небольших различий вычислений с плавающей точкой. Проверка показала совпадение агрегатов (`True`).

В агрегатах по всем транзакциям присутствуют 51 идентификатор: 49 идентификаторов организаций из справочника с транзакциями и два неизвестных идентификатора - 998 и 999.

### Этап G. Построение витрины данных

Витрина строится на основе результата SQL `LEFT JOIN`, поэтому содержит все организации из справочника, в том числе организацию без транзакций.

Витрина содержит поля:

- `org_id` - идентификатор организации;
- `org_name` - название организации;
- `sector` - отрасль;
- `city_name` - город;
- `region_name` - регион;
- `transactions_count` - количество транзакций;
- `total_amount` - общая сумма операций;
- `avg_amount` - средняя сумма операции;
- `last_transaction_date` - дата последней операции.

Полученный размер витрины - **50 строк и 9 столбцов**.

Результат сохраняется в двух форматах:

```text
data/processed/data_mart.csv
data/processed/data_mart.parquet
```

Для записи Parquet используется библиотека `pyarrow`.

### Этап H. Визуализация и BI

На Python строятся и сохраняются два графика:

- общая сумма операций по регионам - `results/plots/region_totals.png`;
- TOP-10 организаций по общей сумме операций - `results/plots/top_organizations.png`.

Дополнительно витрина `data/processed/data_mart.csv` импортируется в Power BI. На одной странице дашборда размещаются визуализации по регионам, TOP-10 организаций и дополнительные графики, построенные только на основе полей витрины.

## 5. Исследование curl и проверка REST API

В этой части работы проверялись версия `curl`, поддерживаемые протоколы, получение данных из REST API, фильтрация, HTTP-заголовки, коды ответа, перенаправления и сохранение ответа в файл. Фактически выполненные команды и их ответы собраны в `results/curl_commands.txt`, сравнение протоколов - в `results/protocol_comparison.md`.

### 5.1. Проверка установки curl и поддерживаемых протоколов

Команды выполнялись в Git Bash из корневой папки проекта:

```bash
curl --version
```

Команда выводит версию `curl`, сведения о сборке и список поддерживаемых протоколов. В рамках лабораторной сравнивались HTTP, HTTPS, FTP, FTPS, SMTP и SMTPS. Наличие протокола в этом списке означает, что установленная сборка `curl` умеет с ним работать; это не означает, что для него запущен сервер.

### 5.2. Запуск API

Перед HTTP-запросами необходимо запустить FastAPI в отдельном терминале:

```bash
uvicorn main:app --reload
```

Все следующие примеры используют адрес `http://127.0.0.1:8000`. Терминал с Uvicorn должен оставаться открытым.

### 5.3. GET: получение списка транзакций

```bash
curl -i http://127.0.0.1:8000/api/transactions
```

`GET` запрашивает ресурс, а параметр `-i` (`--include`) добавляет к телу ответа HTTP-заголовки. В ответе проверяется статус `200 OK` и JSON со списком транзакций.

### 5.4. GET с query-параметром

```bash
curl -i "http://127.0.0.1:8000/api/transactions?currency=RUB"
```

Запрос передаёт параметр `currency=RUB`; API возвращает транзакции, соответствующие фильтру. Кавычки вокруг URL помогают корректно передавать специальные символы и параметры в командной оболочке.

### 5.5. Передача собственного HTTP-заголовка

```bash
curl -i http://127.0.0.1:8000/api/transactions -H "X-Lab-Name: lab2"
```

Ключ `-H` (`--header`) добавляет к запросу заголовок `X-Lab-Name`. Это демонстрирует передачу дополнительных метаданных на стороне клиента.

### 5.6. POST: добавление транзакции

```bash
curl -i -X POST http://127.0.0.1:8000/api/transactions \
  -H "Content-Type: application/json" \
  -d '{"transaction_id":2000,"org_id":10,"date":"2026-10-27","amount":1500.0,"currency":"RUB"}'
```

Здесь `-X POST` задаёт HTTP-метод, `Content-Type: application/json` указывает формат тела запроса, а `-d` передаёт JSON. В выполненном запросе API вернул `200 OK` и данные созданной транзакции.

### 5.7. Проверка метода HEAD

```bash
curl -I http://127.0.0.1:8000/api/transactions
```

`-I` отправляет запрос `HEAD`: сервер должен вернуть заголовки без тела ответа. В нашем эксперименте API ответил `405 Method Not Allowed`. Это означает, что данный маршрут не поддерживает метод `HEAD`; это не означает, что обычный `GET` не работает.

### 5.8. Проверка перенаправления

```bash
curl -i http://127.0.0.1:8000/api/transactions-redirect
```

Команда показывает первоначальный ответ сервера с кодом перенаправления `307` и заголовком `Location`, указывающим целевой адрес. По умолчанию `curl` не переходит по этому адресу автоматически.

```bash
curl -i -L http://127.0.0.1:8000/api/transactions-redirect
```

Параметр `-L` (`--location`) включает автоматический переход по перенаправлению. В результате можно увидеть ответ конечного маршрута `/api/transactions`.

### 5.9. СОхранение команд и выводов

Команды и результаты экспериментов записаны в `results/curl_commands.txt`. В Git Bash оператор `>>` добавляет вывод в конец файла, не перезаписывая уже сохранённое содержимое; `2>&1` направляет туда же сообщения об ошибках. Например:

```bash
curl -i http://127.0.0.1:8000/api/transactions >> results/curl_commands.txt 2>&1
```

Чтобы в файле было понятно, какой результат к какой проверке относится, перед каждым запросом добавлялась текстовая подпись, например:

```bash
 echo "GET: список транзакций" >> results/curl_commands.txt
 curl -i http://127.0.0.1:8000/api/transactions >> results/curl_commands.txt 2>&1
```
